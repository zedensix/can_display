# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

DIY gauge cluster for a 2015 Toyota GT86: C firmware (pico-sdk 2.2, BTstack) for a Raspberry Pi Pico W(H) + ST7789 V2.2 2" 240x320 SPI display, getting car data from an ELM327 BLE OBD dongle (default) or an MCP2515 CAN controller, plus an SDL desktop simulator and host tests that run the same UI code.

## Commands

```sh
mise run sim         # SDL simulator, fake data; arrows turn the encoder, space clicks
mise run test        # host tests of src/app (test/tests.c), ASan + UBSan
mise run firmware    # bin/firmware.uf2 + bin/firmware-sim.uf2; clones the pico-sdk into PICO_SDK_PATH the first time
mise run flash       # build, reboot a running Pico into BOOTSEL (1200 baud touch), dd the UF2; prints each step
mise run flash-sim   # same with the fake-data firmware (SIM=1)
mise run logs        # print the flash log (sends 'l' over USB serial)
mise run logo        # 86.png -> src/app/ui/logo.c (tools/logo.py, then xxd)
mise run logos [dir] # the screensaver's logos, dir/*.png (logos/ by default) in alphabetical order (number them), cropped and fitted -> src/app/ui/brands_data.h: out of git, like logos/ (trademarks); brands.c includes it when there, else the 86 alone
bun run dev          # the web page on localhost:3000, hot reload, its logs in ./data
bun test web         # the log store and parser (a prek hook)
bun run db:generate  # a migration for a change to web/schema.ts (drizzle-kit)
mise run ui          # every screen with fixed readings -> ui/*.png, ui/sheet.png (tools/render_ui.c): rerun after a UI change and look at it
mise run wiring      # the wiring diagram (color, blueprint) -> docs/resources/*.png for docs/wiring.md (Playwright Chromium, fetched once)
bun run wiring       # serves the wiring page (Svelte, tools/wiring) on localhost:3001 and opens it: drag to move, cmd+scroll or pinch to zoom, double-click to fit, click a wire to follow its net, click a board to turn it over (headers in their real order; by default the side you wire from: the Pico from below, mirroring the plan), a button switches BLE dongle / wired MCP2515; its Dimensions tab edits every module's dimension (checked or guessed; hovering a row highlights it on the drawings), saving each as it's typed to faceplate/data/measured.json (and the browser until the server has it), then rerunning mise run faceplate; a value the model refuses stays saved, the page says why
mise run faceplate   # the printed parts (scad-js, one class per part, dimensions in faceplate/model/config.ts, overridden by the measured ones in faceplate/data/measured.json): faceplate (display + encoder) and tray (Pico components out with its pins and plugs through 2 slots, the converter with its ears cut off, MCP2515), no bigger than the faceplate -> faceplate/stl/*.stl (binary, openscad-wasm) + faceplate/renders/*.png (OpenSCAD from mise; the assembly ones with every module modeled in place, `faceplate/model/mockups.ts`) + faceplate/data/dimensions.json for the wiring page's Dimensions tab: rerun after a change and look at them
mise run assembly    # opens faceplate/renders/assembly.scad (written by mise run faceplate: both parts with every module modeled in place) in OpenSCAD's window, to turn it around in 3D; F5 keeps the colors
mise install         # the pinned tools, then the git hooks (`prek install`, mise.toml's postinstall): clang-format, biome, `bun check` (types: never a package.json `check` script, which would shadow it), web and host tests
prek run --all-files # every hook on every tracked file
```

The ARM toolchain (14.3.Rel1), CMake, Ninja, Python, Bun, prek, OpenSCAD (a nightly snapshot) and the SDK version/path are pinned in `mise.toml`; the web and tooling packages (Svelte and its Bun plugin, Tailwind, Biome, Playwright, scad-js, openscad-wasm) in `package.json`. The web pages are Svelte 5 components (no SvelteKit), bundled by `Bun.serve` from an HTML import with `bun-plugin-svelte` (bunfig.toml). Our sources build with `-Wall -Wextra -Werror` on every target (SDK sources excepted): a warning is a failed build, there's no C linter beyond it; clang-format (`.clang-format`) formats the C, Biome (`biome.json`) lints and formats the TypeScript, Svelte (its experimental full HTML support), CSS and JSON, both through the prek hooks. The CI (GitHub Actions) runs every hook (`prek run --all-files`) and builds the firmware on Ubuntu: the host tests build with gcc there, whose `-Wformat-truncation` clang doesn't have (use what `snprintf` returns).

This project started in Go/TinyGo and was rewritten in C (see git history before `cbb43b4`): TinyGo's cooperative scheduler, 8KB goroutine stacks, fonts in RAM and its USB and BLE stacks kept breaking on the Pico W.

## Architecture

Data flows one way: **source -> `state_t` -> `ui_render(canvas, state, screen, settings, now)` -> panel**.

- `src/app` is hardware-free C shared by the firmware, the simulator (`sim/`) and the tests (`test/`): signals, OBD/GT86 decoding, the ELM327 session, sensors math, settings encoding, the flash log ring, encoder navigation, gfx and the UI. Anything testable goes there.
- `src/firmware` is the Pico side: `board.h` (pins), `display.c` (ST7789 init, PWM backlight, flip via MADCTL, async DMA push of 16-bit frames), `knob.c` (encoder on GPIO IRQ with a quadrature table, detents counted at rest so a lost step can't shift them; button debounced, a click acts on press; the loop redraws at once on input via `knob_has_new_input`), `store.c` (flash log, settings, serial dump), `ble.c`, `mcp2515.c`, `main.c`.
- Single loop, no RTOS: `pico_cyw43_arch_poll`, so BTstack runs only when `ble_poll_radio` calls `cyw43_arch_poll()`: between frames, and while the DMA pushes one. Nothing may block the loop.
- A Bluetooth failure says what the code means on the panel, the code after it (`ble_error`: HCI and BTstack codes, "can't connect: the radio still holds another connection (0x56)").
- `ble.c` is a phase machine: prompt -> start (cyw43 + BTstack) -> scan (30s timeout, matches name hints or `profiles` services, or `ELM_ADDRESS`) -> connect -> GATT discovery (logs every service/characteristic) -> notifications -> `elm_t` session. Writes are "without response"; a command the stack can't take yet stays pending for the next poll.
- `elm327.c` is a non-blocking ELM327 session: init script (ATZ, echo/spaces off, headers on, ATSP6, ATSH7DF), probes whose raw answers are logged (ATI, ATRV, 0100/0120/0140 supported-PID bitmaps, 010C, and `010C24050F111`: if its answer holds all five PIDs, polling asks for them in one request), then a poll cycle (that one request, or RPM every other request between AFR, throttle, coolant and intake one at a time; ATRV every second, and every 3s the drive mode (0x0D3, broadcast: `elm_mode.c` stops polling for a raw monitor of that ID alone, ATCAF0, ATCRA0D3, ATMA until its first frame or 400ms, then ATCRA, ATCAF1; dropped after 3 monitors without it while the ECU answers), and the engine ECU's own reads: ATSH7E0, 2101 for the oil temperature, `ETHANOL_RAM_READ` for the ethanol %, ATSH7DF, each dropped after 3 answers without its value while the ECU answers the rest). Multi-frame answers are reassembled by `isotp_add_frame`. Timeouts resend `ELM_RETRIES` times. With headers on each reply line is a CAN frame, decoded by `obd_decode_frame` (ECU1 0x7E8, 11bit IDs only). The "1" response-count suffix is dropped if the dongle answers `?`. "Scan ECU RAM" in the settings (`elm_request_ram_scan`) suspends polling to read the engine ECU's RAM and log ethanol % candidates (see below), with its progress as the status. "Listen CAN" (`elm_request_can_listen`, `sniff.c`) looks for the VSC / TRC OFF mode's bits: it prompts 5 steps (everything on, TRC OFF, on, everything off, on), each listened to once the driver clicks (`ble_handle_click` -> `elm_listen_click`); the dongle monitors one window of 256 IDs at a time (ATCAF0, ATCM700, ATCF, ATMA, frames fed line by line as they stream), twice over the bus per step; a bit changing within a step is noise, a candidate is quiet within every step, the same in the "on" steps and different between modes (by bit, not by ID: a flag shares its frame with a rolling counter); the candidates are logged with their data per mode and the session restarts with ATZ. A first run found them in 0x0D3 (byte 0 bit 5 TRC off, byte 1 bit 3 VSC off, byte 3 bit 0 VSC on): one run, unconfirmed.
- Connection control: without auto-connect the source waits on READY (`state_t.wait`: the knob picks CONNECT or SETTINGS, `screen_apply_input`) while the radio scans in the background and names the dongle CONNECT connects to straight away (the last one connected to, kept in the settings, if it's around; else the first seen), by name: the advertised one, else the GAP device name (2A00) read at each connection and kept with it, else the address; a failure waits for a click to retry (auto-connect: retries after 5s). OFFLINE offers the same choice. Nothing connected and no input for `SCREEN_IDLE_MS` (30s), the screensaver (`ui_showcar.c`: the 86's logo, then the logos of the parts on the car (`mise run logos`, kept out of git), one at a time, fading in and out rising, a shine across each, dots for which one) takes the screen in full frames; the next input only wakes it. In the simulator, r shows a READY prompt to try both. `main.c` hands a click to `ble_handle_click` only on the gauges page. A retry is `watchdog_reboot` with `CONNECT_NOW` in watchdog scratch 0, so the next boot connects without asking.
- Standby: once polling, if the engine ECU hasn't answered anything for `CAR_OFF_MS` (90s), `ble.c` disconnects (so the dongle, always powered by the OBD port, can sleep) and powers the radio off; `main.c` puts the panel to sleep and stops drawing. A click reboots to connect. It saves what software can: a Pico on an always-live supply still draws ~20mA.
- `screen_t` is what the encoder drives: on the gauges, turning cycles views (grid, then each gauge alone, its value drawn 2-3x by `gfx_text`'s scale instead of a bigger font); a click opens the settings page (one screen, no scrolling: groups DISPLAY, CONNECTION, TOOLS, then a BACK button; values drawn as controls: a segment bar, switches, a BLE | CAN choice, chevrons on actions; buttons (`draw_button`: an icon and a capitalized label, not caps), switches and the row under the cursor are anti-aliased pills (`fill_round_rect`), round like the spinner; brightness, shift light RPM, data source: the BLE dongle or the MCP2515, saved and applied by a reboot when leaving the page, the rows needing the dongle dimmed and inert with CAN; auto-connect, flip; Scan ECU RAM, Listen CAN, Disconnect: `ble_go_offline` lets the dongle go and powers the radio off with the screen on, naming the dongle; a click powers the radio back on and connects straight to it, no reboot), which `main.c` applies at once and saves to flash when leaving the page. A 1s hold reboots.
- `state_t.status` is the source's report while it isn't delivering: while non-empty, the gauges page draws a status screen (title, wrapped lines, spinner) instead of the tiles. A reading older than its tile's `stale_ms` renders as "--" (2s, 10s for the oil temperature polled every 3s). At power-on `ui_render_boot` shows a spinner whose ring closes into the logo's circle as the logo fades in. The spinner (boot and status screens) is drawn per pixel, anti-aliased, from a quadrant of the ring worked out once (`ring_px`). While it's the only thing moving (the boot animation, a status screen whose text doesn't change), `main.c` draws and pushes only its rows (`ui_spinner_rows`) back to back, about three times the normal frame rate.
- Data log (`datalog.c`): 32-byte records every 200ms while RPM comes in (the gauges): 8 readings, the throttle last (older records hold 0xFFFF there, read as none), room for 4 more in the record's free bytes without shortening the ring (~950KB, ~100 minutes of driving), a new session each boot, in a flash ring written page by page (a power cut loses under 2s). "Send log" lets the dongle go and makes the dash a BLE peripheral ("GT86 DASH", `dash.gatt`): the page in `web/` (Chrome on Android, served over https for Web Bluetooth: Svelte, Bun's `Bun.serve` with an HTML import, Tailwind through `bun-plugin-tailwind`; `package.json`, `bunfig.toml` and the `Dockerfile` to self-host it are at the root) writes 'S', gets a 4-byte size then the log from its oldest record as notifications, writes 'D' once it has it all (the dash shows "downloaded" and goes back to scanning for the dongle, as a click does, no reboot; only once the phone's disconnection is in: BTstack holds a single connection, `MAX_NR_HCI_CONNECTIONS 1`, and connecting before gets `BTSTACK_MEMORY_ALLOC_FAILED`, 0x56), and sends the raw log to its server (`POST /api/sessions`), which keeps every sample once, keyed by session and time since boot, in SQLite through Drizzle (`web/schema.ts`; `bun run db:generate` writes a migration to `web/drizzle/`, applied when the server starts; `DATA_DIR`, the image's `/data` volume). The page lists the stored sessions (paged, searched by name or number, filtered by the day the server got them: the dash has no clock), names them, and charts each one; theme light, dark or the device's (`theme.ts`, a `.dark` class, the colors as CSS variables); no login: the https reverse proxy authenticates. Its parser in `web/datalog.ts` must follow `datalog.h`'s record layout; `bun test web` checks the store.
- Thresholds are the `*_RANGE` macros at the top of `src/app/ui/ui.c`; `ui_tiles` wires labels, formats and units onto them.
- The look copies the GT86's own cluster: black, red-orange around the readings (`accent`), white labels; readings take their band's color: green fine, amber warns, a reading in danger blinks its whole tile red, blue is an engine not warm yet (oil under 80°C, coolant under 70°C: not alarms, every cold start goes through them). From `OIL_CRITICAL` (130°C) the oil temperature takes the whole screen, on every page. With the stability control off (`state_drive_mode`: 0x0D3 decoded by `gt86_decode_broadcast`, from the MCP2515 as it streams or the dongle's monitor; a mode older than 10s counts as normal), the grid becomes the track layout (`draw_track_grid`): oil and AFR across the screen, coolant and intake under them, a TRC OFF (amber) or VSC OFF (red) badge; the views of one gauge alone stay as they are. In the simulator, m steps through the modes. Off the throttle (`state_off_throttle`: the throttle PID 0x11 within `THROTTLE_CLOSED_MARGIN` of its lowest since boot, or so 1s ago) the AFR, lean from the deceleration fuel cut, is drawn white with no alarm; the MCP2515 source requests the throttle and the AFR in turn. Gauges are segments colored by the band each stands for, the unlit ones faintly so the red zone shows at rest; a gauge alone is a round dial like the tachometer, with the session's min and max (`reading_t`, since boot) and its peak marked. No RPM tile (the car's tachometer is in front of the driver): RPM drives the shift light, a race wheel's LED bar across the top of the gauges, 20 narrow LEDs lighting in pairs from both ends over the last 1500 rpm (green, amber, red), all flashing blue from the shift RPM.

Adding a signal: a `signal_t` value, a decoder case in `obd.c`, a tile + range in `ui.c`, a poll entry in `elm327.c` if it's a PID, `simdata.c`, and tests.

## Conventions and gotchas

- Every doc is in English: README, `docs/`, `faceplate/README.md`, this file, and `TODO.md` (its tasks too), as are code comments and log lines.
- The C sits in subfolders by category under `src/app` and `src/firmware`; an include is the path from one of those two roots (`#include "ui/ui.h"`), a header of the same folder bare. A module split across files by role shares its state through its `*_internal.h`, never through the public header.
- A code file stays under about 300 lines (generated ones aside: `fonts.c`, `logo.c`): past that, split it by what it does (a module, a page, a test group), not by line count.
- CAN IDs and formulas come from community reverse-engineering and are **unverified on this car**. Verified on this car so far: the oil temp via Mode 21 PID 01 (byte AC - 40), and that the ECU lists PID 0x24 (AFR) as supported, not 0x52 (ethanol) nor 0x5C (oil). On its memory: Subaru SSM reads (A0) get no answer; UDS ReadMemoryByAddress (`23 14` + 4 address bytes + 1 size byte, header 7E0) reads RAM from 0xFFF80000 without security access but answers 7F 23 33 (security access denied) on ROM. The ethanol % is a big-endian float at 0xFFF87C7C in the engine ECU's RAM (`ETHANOL_RAM_READ`), found by three RAM scans and matched against OFT (2026-11-16): this tune's layout, a reflash may move it. In `ble.c`, only the 18F0 GATT profile is confirmed (on the Vgate iCar Pro 2S); the others are guesses. Don't present any of them as confirmed. `docs/can-reverse-engineering.md` covers how to verify them.
- RAM: the full frame (153.6KB) is a static array, BTstack and cyw43 use static pools: overflow is a link error, not a runtime surprise. If a change doesn't link, `canvas_t` supports drawing in bands (draw and push per band).
- Flash, from the end of the 2MB: BTstack's own two sectors (`pico_btstack_flash_bank`), the 64KB log ring, the settings sector, then the data log down to the first megabyte. `store_init` refuses to touch flash if the firmware ever reaches the settings sector, and turns the data log off if it reaches the first megabyte. Flash writes go through `flash_safe_execute` (interrupts off): `log_line` is for events only, never per frame or per OBD reply.
- Crashes leave a trace: the watchdog (8s, fed once per loop) reboots a frozen board and the next boot logs it; `PICO_PANIC_FUNCTION=crash_panic` writes the panic message to the flash log; `isr_hardfault` marks watchdog scratch 1 and the next boot logs it.
- USB serial is TinyUSB (`pico_stdio_usb`): the 1200 baud touch reboots into BOOTSEL, which `mise run flash` relies on.
- Hardware facts that constrain the code (see `docs/wiring.md`): the RP2040 is not 5V tolerant (MCP2515 SO line needs level shifting, the encoder is wired on its legs with the Pico's internal pull-ups, its board's + never on 5V). GPIO23/24/25/29 belong to the wireless chip, GP15 to the SDK's RP2040-E5 USB workaround.
- Pin constants in `src/firmware/board.h` and the tables in `docs/wiring.md` must stay in sync. Same for the panel size in `board.h` and `sim/main.c`.
