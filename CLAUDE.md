# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

DIY gauge cluster for a 2015 Toyota GT86: C firmware (pico-sdk 2.2, BTstack) for a Raspberry Pi Pico W(H) + ST7789 V2.2 2" 240x320 SPI display, getting car data off the CAN bus through an MCP2515 CAN controller, handing its data log to a phone over BLE, plus an SDL desktop simulator and host tests that run the same UI code.

## Commands

```sh
mise run sim         # SDL simulator, fake data (a tour of scenarios, simdata.c); arrows turn the encoder, space clicks, l landscape, m drive mode, r the MCP2515 waiting for the car
mise run test        # host tests of src/app (test/tests.c), ASan + UBSan
mise run firmware    # bin/firmware.uf2 + bin/firmware-sim.uf2; clones the pico-sdk into PICO_SDK_PATH the first time
mise run flash       # build, reboot a running Pico into BOOTSEL (1200 baud touch), dd the UF2; prints each step
mise run flash-sim   # same with the fake-data firmware (SIM=1): the simulator's tour of scenarios on the panel
mise run logs        # print the flash log (sends 'l' over USB serial)
mise run logo        # 86.png -> src/app/ui/logo.c (tools/logo.py, then xxd)
mise run logos [dir] # the screensaver's logos, dir/*.png (logos/ by default) in alphabetical order (number them), cropped and fitted -> src/app/ui/brands_data.h: out of git, like logos/ (trademarks); brands.c includes it when there, else the 86 alone
bun run dev          # the web page on localhost:3000, hot reload, its logs in ./data
bun test web         # the log store and parser (a prek hook)
bun run db:generate  # a migration for a change to web/schema.ts (drizzle-kit)
mise run ui          # every screen with fixed readings -> ui/*.png, ui/sheet.png (tools/render_ui.c): rerun after a UI change and look at it
mise run wiring      # the wiring diagram (color, blueprint) -> docs/resources/*.png for docs/wiring.md (Playwright Chromium, fetched once)
bun run wiring       # serves the wiring page (Svelte, tools/wiring) on localhost:3001 and opens it: drag to move, cmd+scroll or pinch to zoom, double-click to fit, click a wire to follow its net, click a board to turn it over (headers in their real order; by default the side you wire from: the Pico from below, mirroring the plan); its Dimensions tab edits every module's dimension (checked or guessed; hovering a row highlights it on the drawings), saving each as it's typed to faceplate/data/measured.json (and the browser until the server has it), then rerunning mise run faceplate; a value the model refuses stays saved, the page says why
mise run faceplate   # the printed parts (scad-js, one class per part, the modules' dimensions in faceplate/shared/config.ts, each model's own in its folder's config.ts, overridden by the measured ones in faceplate/data/measured.json): faceplate (display + encoder) and tray (Pico components out with its pins and plugs through 2 slots, the converter with its ears cut off, MCP2515), no bigger than the faceplate; or the vent pod (`pod.ts`: a face shaped like the vent's gauge adapter, the display in landscape and the encoder under it, a can into the duct with a sled carrying the boards); or the head (`head.ts`: the smallest box, for up high, the display in landscape and the Pico behind it, its lid clipped on and carrying the Pico, the boards on heat-staked pins; the MCP2515, the converter and the encoder on a cable); or the bar (`bar.ts`: one long, thin box on the steering column's shroud, its bottom hollowed into an arc, the head's display and Pico (`shared/case.ts`) in the middle, its lid a tray deep enough for the wires, a skirt into the shell with bumps into its slots (snap tabs broke), the encoder and the converter's plug on one side, the MCP2515 on the other; the converter on the cable) -> each model's stl/*.stl (binary, openscad-wasm) + renders/*.png (OpenSCAD from mise; the assembly ones with every module modeled in place, `mockups.ts`) + faceplate/data/dimensions.json for the wiring page's Dimensions tab: rerun after a change and look at them
mise run assembly    # opens faceplate/plate/renders/assembly.scad (written by mise run faceplate: both parts with every module modeled in place) in OpenSCAD's window, to turn it around in 3D; F5 keeps the colors
mise run pod         # the same for the vent pod: faceplate/pod/renders/pod.scad, every module in place, the can cut open
mise run head        # the same for the head: faceplate/head/renders/head.scad, the display and the Pico in place
mise run bar         # the same for the bar: faceplate/bar/renders/bar.scad, every module in place
mise run android:build # the Android Auto app's debug APK (android/, Gradle from mise, its SDK packages by mise run android:sdk)
mise run android:flash # build and install the app on the phone (the first one adb sees, USB or Wi-Fi debugging, emulators skipped) and open it
mise run android:run [scene [view]] # build, install on the phone or emulator (adb) and open its preview; a scene (street, track, race, cold, alarm, stale) holds fixed readings, for screenshots (adb exec-out screencap -p)
mise run android:test  # the app's unit tests (the live frame's decoder against the dash's bytes)
mise run android:dhu   # the desktop head unit (Android Auto on the laptop) from the phone on USB, its head unit server started in Android Auto's developer settings
mise install         # the pinned tools, then the git hooks (`prek install`, mise.toml's postinstall): clang-format, biome, `bun check` (types: never a package.json `check` script, which would shadow it), web and host tests
prek run --all-files # every hook on every tracked file
```

The ARM toolchain (14.3.Rel1), CMake, Ninja, Python, Bun, prek, OpenSCAD (a nightly snapshot), Java 21, the Android SDK, Gradle and the pico-sdk version/path are pinned in `mise.toml` (the CI leaves the Android ones out: it doesn't build the app); the web and tooling packages (Svelte and its Bun plugin, Tailwind, Biome, Playwright, scad-js, openscad-wasm) in `package.json`. The web pages are Svelte 5 components (no SvelteKit), bundled by `Bun.serve` from an HTML import with `bun-plugin-svelte` (bunfig.toml). Our sources build with `-Wall -Wextra -Werror` on every target (SDK sources excepted): a warning is a failed build, there's no C linter beyond it; clang-format (`.clang-format`) formats the C, Biome (`biome.json`) lints and formats the TypeScript, Svelte (its experimental full HTML support), CSS and JSON, both through the prek hooks. The CI (GitHub Actions) runs every hook (`prek run --all-files`) and builds the firmware on Ubuntu: the host tests build with gcc there, whose `-Wformat-truncation` clang doesn't have (use what `snprintf` returns).

This project started in Go/TinyGo and was rewritten in C (see git history before `cbb43b4`): TinyGo's cooperative scheduler, 8KB goroutine stacks, fonts in RAM and its USB and BLE stacks kept breaking on the Pico W.

## Architecture

Data flows one way: **source -> `state_t` -> `ui_render(canvas, state, screen, settings, now)` -> panel**.

- `src/app` is hardware-free C shared by the firmware, the simulator (`sim/`) and the tests (`test/`): signals, OBD/GT86 decoding, the MCP2515 self test's verdicts, sensors math, settings encoding, the flash log ring, encoder navigation, gfx and the UI. Anything testable goes there.
- `src/firmware` is the Pico side: `board.h` (pins), `display.c` (ST7789 init, PWM backlight, flip via MADCTL, async DMA push of 16-bit frames), `knob.c` (encoder on GPIO IRQ with a quadrature table, detents counted at rest so a lost step can't shift them; button debounced, a click acts on press; the loop redraws at once on input via `knob_has_new_input`), `store.c` (flash log, settings, serial dump), `ble.c` (Send log), `mcp2515.c`, `source.c` (the data source, reboots, crash marks), `main.c`.
- Two cores, one loop, no RTOS: core1 only reads the CAN bus (`bus_reader`, below); core0 runs everything else from the main loop, `pico_cyw43_arch_poll`, so BTstack runs only when `ble_poll_radio` calls `cyw43_arch_poll()`: between frames, and while the DMA pushes one. Nothing may block the loop.
- MCP2515 self test (`mcp2515_selftest.c`, its verdicts in `src/app/obd/mcp_check.c`): every boot checks SPI (CANSTAT after a reset, a register read back), loopback (a frame to itself), then listens to the bus in listen-only mode (never transmitting) until 10 frames came in, before normal mode and the OBD requests; each failure says which wire to check, with Retry (a reboot, `mcp2515_wants_retry`) and Settings; a bus silent for 5s says WAITING FOR THE CAR instead, no Retry (the Pico powered before the ignition wakes the bus, most boots): it keeps listening and passes once frames come, the screensaver over it after `SCREEN_IDLE_MS` (any status counts as nothing coming in). Retry and Settings are the only buttons a status screen has (`state_t.wait`: `WAIT_RETRY`); a click on the gauges page goes to `give_click_to_prompt` (`source.c`) first. A 1s hold reboots.
- Bluetooth (`ble.c`): the dash as a BLE peripheral, "GT86 DASH" (`dash.gatt`), on the air from boot (`ble_start`) for one phone, its apps sharing the link: the Android Auto app subscribes to the live readings, a 17-byte frame every 50ms (`live_encode`, `src/app/data/live.h`; the app's `LiveFrame` must follow it, both pinned on the same bytes by `test_live.c` and `LiveFrameTest.kt`); Send log's page reads the data log. BTstack writes flash (its ER/IR keys at the radio's first start on a board, bonding) through the SDK's `flash_safe_execute`, and so do we: `store.c` replaces the SDK's flash safety helper (`get_flash_safety_helper`, weak) with one that holds core1, which runs from flash, in RAM through every write (multicore lockout) once it's a lockout victim, interrupts off; the SDK's own lockout is off (`PICO_FLASH_SAFE_EXECUTE_PICO_SUPPORT_MULTICORE_LOCKOUT=0`): it refuses every write while core1 isn't running. Send log pauses the CAN source, the gauges and the data log with it (no record written over the ring while it's read out); the status before it comes back after.
- `screen_t` is what the encoder drives: on the gauges, turning cycles views (every gauge: `ui_main.c`, the oil first and big with its session's highest, the other tiles as a list of rows, label, short bar, value; then each gauge alone, then the pedal and the load, views only (`ui_tile_count` of `ui_tiles` make the main view, the first the oil, `ui_view_count` the views), its value drawn 2-3x by `gfx_text`'s scale instead of a bigger font); a click opens the settings page (one screen in portrait: groups DISPLAY, TOOLS, then a BACK button; in landscape the list scrolls to keep the cursor's row in the middle, Back fixed under it; values drawn as controls: a segment bar, switches, a chevron on Send log; buttons (`draw_button`: an icon and a capitalized label, not caps), switches and the row under the cursor are anti-aliased pills (`fill_round_rect`), round like the spinner; brightness, shift light RPM, flip, landscape; Send log), which `main.c` applies at once and saves to flash when leaving the page. The ELM327 BLE dongle was the other data source, with its own tools (Scan ECU RAM, Listen CAN): taken out, its code in `9dc0432`.
- Orientation: `settings_t.flip` (a half turn) and `settings_t.landscape` (a quarter turn, MADCTL's MV: the same 153.6KB frame as 320x240) make 4; the canvas's width and height follow, and every screen lays itself out from them (`is_landscape`: the oil on the left of the list, the track layout 2 by 2, a dial with its extremes in a column beside it, the status text beside the ring, the oil overheat on one line). `main.c` and the simulator pick the canvas's size from the setting, applied at once.
- A door or the boot open (`state_doors`: `DOOR_*` bits, fresh for 10s) takes the gauges page, after the oil overheat (`ui_doors.c`): the car from above, front up, left-hand drive, the open one swung out in red, which ones in words, and a Dismiss button: a click puts it away (`screen_t.doors_dismissed`) until another door opens, or one shut opens again. Their bits are 0x375's byte 1 (`GT86_ID_DOORS`, found by a Listen CAN run, engine off), from the MCP2515 as it streams.
- The info strip (`ui_strip.c`) runs along the bottom of the gauges page, every view: the gear (`state_gear`: RPM over speed against the manual gearbox's ratios, 4.1 final drive, 215/45R17; N with the clutch in or under 5 km/h), the outside temperature (PID 0x46), and the odometer if the ECU answers 01A6, else the trip (`state_t.trip_km`, the speed readings added up). No labels: the units say what each is.
- `state_t.status` is the source's report while it isn't delivering (the self test, Send log): while non-empty, the gauges page draws a status screen (title, wrapped lines, spinner) instead of the tiles. A reading older than its tile's `stale_ms` renders as "--" (2s; 10s for the temperatures, slow to change, and the ethanol %, in the MCP2515's slower round of requests). At power-on `ui_render_boot` shows a spinner whose ring closes into the logo's circle as the logo fades in. The spinner (boot and status screens) is drawn per pixel, anti-aliased, from a quadrant of the ring worked out once (`ring_px`). While it's the only thing moving (the boot animation, a status screen whose text doesn't change), `main.c` draws and pushes only its rows (`ui_spinner_rows`) back to back, about three times the normal frame rate.
- Data log (`datalog.c`): 64-byte records (a 256-byte page holds 4, none straddles one) every 200ms while RPM comes in: 16 readings (the gauges', the throttle, pedal, load, timing, both fuel trims, commanded AFR, DI rail pressure, speed), room for 12 more (~950KB, ~50 minutes of driving); older firmware's 32-byte records (kind 1, 8 readings) may sit in the ring before them: the firmware (`datalog_open`) and the web parser walk it by each record's kind, a new record starting at a 64-byte boundary, a new session each boot, in a flash ring written page by page (a power cut loses under 2s). "Send log" hands it over the dash's BLE link (Bluetooth, above): the page in `web/` (Chrome on Android, served over https for Web Bluetooth: Svelte, Bun's `Bun.serve` with an HTML import, Tailwind through `bun-plugin-tailwind`; `package.json`, `bunfig.toml` and the `Dockerfile` to self-host it are at the root) writes 'S', gets a 4-byte size then the log from its oldest record as notifications, writes 'D' once it has it all (the dash shows "downloaded" and goes back to the gauges 2.5s later, as a click does), and sends the raw log to its server (`POST /api/sessions`), which keeps every sample once, keyed by session and time since boot, in SQLite through Drizzle (`web/schema.ts`; `bun run db:generate` writes a migration to `web/drizzle/`, applied when the server starts; `DATA_DIR`, the image's `/data` volume). The page lists the stored sessions (paged, searched by name or number, filtered by the day the server got them: the dash has no clock), names them, and charts each one; theme light, dark or the device's (`theme.ts`, a `.dark` class, the colors as CSS variables); no login: the https reverse proxy authenticates. Its parser in `web/datalog.ts` must follow `datalog.h`'s record layout; `bun test web` checks the store.
- Thresholds are the `*_RANGE` macros at the top of `src/app/ui/ui.c`; `ui_tiles` wires labels, formats and units onto them.
- The look copies the GT86's own cluster: black, red-orange around the readings (`accent`), white labels; readings take their band's color: green fine, amber warns, a reading in danger blinks its whole tile red, blue is an engine not warm yet (oil under 80°C, coolant under 70°C: not alarms, every cold start goes through them). From `OIL_CRITICAL` (130°C) the oil temperature takes the whole screen, on every page. With the stability control off (`state_drive_mode`: 0x0D3 decoded by `gt86_decode_broadcast`, from the MCP2515 as it streams; a mode older than 10s counts as comfort, as does any with the engine off: contact on, 0x0D3 reads as everything off), the grid becomes the track layout (`draw_track_grid`): oil and AFR across the screen, coolant and intake under them, a badge naming the mode: SPORT MODE (VSC sport, the accent), DRIFT MODE (TRC off) or TRACK MODE (both, amber), RACE MODE (everything off: TRC OFF held 3s, red); everything on is comfort, the normal grid; the views of one gauge alone stay as they are. In the simulator, m steps through the modes. Off the throttle (`state_off_throttle`: the throttle PID 0x11 within `THROTTLE_CLOSED_MARGIN` of its lowest since boot, or so 1s ago) the AFR, lean from the deceleration fuel cut, is drawn white with no alarm; the MCP2515 requests what isn't broadcast, a PID every 40ms: the AFR, throttle, pedal, load, intake, the ECU's voltage (PID 0x42, a few tenths under the battery's) and the speed (the gear wants it under 2s old), then the next of the slower ones, the ethanol % among them (`obd_build_ethanol_read`, the RAM read as a frame to 0x7E0); its acceptance filters let in only the frames read (0x7E8 and the doors in RX buffer 0, no rollover; RPM, drive mode, temperatures in buffer 1): polled between frames drawn, unfiltered, a rare frame was almost always lost. Once running, core1 alone talks to the chip (`bus_reader`): it reads both buffers as fast as SPI goes into a queue core0 decodes, and sends the requests; from core0 between frames drawn, the temperatures' 20Hz frame, in phase with the loop's 50ms, was lost for seconds on end. A flash write holds core1 in RAM (the flash safety helper in `store.c`, multicore lockout; see Bluetooth above). The first minute running, it counts each filtered ID's frames, and those the queue had no room for, and logs the counts once. Gauges are segments colored by the band each stands for, the unlit ones faintly so the red zone shows at rest; a gauge alone is a round dial like the tachometer, with the session's min and max (`reading_t`, since boot) and its peak marked. No RPM tile (the car's tachometer is in front of the driver): RPM drives the shift light and, from `LIMITER_FLASH_RPM` (7300, near the 7600 limiter), flashes the whole gauges page red with SHIFT across it; a race wheel's LED bar across the top of the gauges, 20 narrow LEDs lighting in pairs from both ends over the last 1500 rpm (green, amber, red), all flashing blue from the shift RPM.

- The Android Auto app (`android/`, Kotlin, `com.zedensix.gt86dash`, the Car App Library): a navigation app, the one kind Android Auto lets draw its own screen, its "map" the gauges, drawn with Android's Canvas on the surface the host hands it (`SurfaceRenderer`, 30 fps, inside the visible area), its action strip the previous and the next view (as the encoder turns them) and a cog for the settings, in Android Auto's own templates (`SettingsScreen.kt`: a list, the shift light's RPM in a pane, ±100 per press as on the Pico, Off below 5000; the min and max reset), the only part of a navigation app's UI it doesn't draw itself. Not the C UI: its own look (`Pages.kt`, Barlow Condensed, OFL, in `res/font`), laid out in an 800x480 screen's pixels less the host's rail (692x460) and scaled; the same bands and colors, `Gauges.kt` a copy of `ui.c`'s `*_RANGE` and `ui_tiles` that must stay in step. The same pages full screen on the phone (`PreviewActivity`), inside the safe area (the window insets: the camera's cutout, the system bars; Android 13 and up, minSdk 33: its Bluetooth calls without the deprecated ones), plain Views: the gauges in landscape with arrows on either side, the waiting screen in portrait (`PreviewActivity` turns itself from what `Dash.frame` drew, kept through the turn by `configChanges`: recreated, it would drop the link); the cog opens a settings page of its own (`SettingsActivity`, two columns in landscape): the link's state with what it needs (Allow Bluetooth, Turn Bluetooth on), the dash to connect to (any, the first found, or one picked by its address from those its own scan sees, saved in `Settings.dash`, `LiveLink.use`; a connected dash doesn't advertise, so it lists as connected), then the gauges' settings. The settings are the phone's (`Settings.kt`, SharedPreferences), the min and max one `Extremes` for both screens. Its readings are the dash's (`Live.kt`: `LiveLink` scans for its service (and its address once picked), connects, subscribes, and starts over when the link drops; a waiting screen says what it waits for: Bluetooth's permissions, Bluetooth on, the dash), or made up (`FakeSource`) with Demo on in the settings; the simulator's firmware (`mise run flash-sim`) streams its made-up tour too. A debug build answers any host (the desktop head unit); in the car, Android Auto runs only apps from a trusted source, the Play Store (an internal test track).

Adding a signal: a `signal_t` value, a decoder case in `obd.c`, a tile + range in `ui.c` if it's shown, a poll entry in `mcp2515.c` if it's a PID, a data log column (`datalog.c`, `web/datalog.ts`'s `LAYOUT`, `web/schema.ts` and a migration, a chart in `SessionPage.svelte`), `simdata.c`, the live frame (`live.h`, `Live.kt`, both tests) and the Android app's `Readings` and `Gauges.kt` if it's shown there, and tests.

## Conventions and gotchas

- Every doc is in English: README, `docs/`, `faceplate/**/README.md`, this file, and `TODO.md` (its tasks too), as are code comments and log lines.
- `.gitignore` rules are anchored at the root (`/data/`, `/logos/`): a bare `data/` once ignored `src/app/data/` too, and the CI couldn't build what never reached the repository.
- The C sits in subfolders by category under `src/app` and `src/firmware`; an include is the path from one of those two roots (`#include "ui/ui.h"`), a header of the same folder bare. A module split across files by role shares its state through its `*_internal.h`, never through the public header.
- A code file stays under about 300 lines (generated ones aside: `fonts.c`, `logo.c`): past that, split it by what it does (a module, a page, a test group), not by line count.
- CAN IDs and formulas come from community reverse-engineering; every signal the dash reads is checked on this car, in use (the user says when one reads wrong). On the ECU: it lists PID 0x24 (AFR) as supported, not 0x52 (ethanol) nor 0x5C (oil); the oil temp also answers Mode 21 PID 01 (byte AC - 40, the dongle's, not asked since). On its memory: Subaru SSM reads (A0) get no answer; UDS ReadMemoryByAddress (`23 14` + 4 address bytes + 1 size byte, header 7E0) reads RAM from 0xFFF80000 without security access but answers 7F 23 33 (security access denied) on ROM. The ethanol % is a big-endian float at 0xFFF87C7C in the engine ECU's RAM (`ETHANOL_RAM_READ`), found by three RAM scans and matched against OFT (2026-11-16): this tune's layout, a reflash may move it. `docs/can-reverse-engineering.md` covers how they were found and how to check them on another car.
- RAM: the full frame (153.6KB) is a static array, BTstack and cyw43 use static pools: overflow is a link error, not a runtime surprise. If a change doesn't link, `canvas_t` supports drawing in bands (draw and push per band).
- Flash, from the end of the 2MB: BTstack's own two sectors (`pico_btstack_flash_bank`), the 64KB log ring, the settings sector, then the data log down to the first megabyte. `store_init` refuses to touch flash if the firmware ever reaches the settings sector, and turns the data log off if it reaches the first megabyte. Flash writes go through `flash_safe_execute` (interrupts off): `log_line` is for events only, never per frame or per OBD reply.
- Crashes leave a trace: the watchdog (8s, fed once per loop) reboots a frozen board and the next boot logs it; `PICO_PANIC_FUNCTION=crash_panic` writes the panic message to the flash log; `isr_hardfault` marks watchdog scratch 1 and the next boot logs it.
- USB serial is TinyUSB (`pico_stdio_usb`): the 1200 baud touch reboots into BOOTSEL, which `mise run flash` relies on.
- Hardware facts that constrain the code (see `docs/wiring.md`): the RP2040 is not 5V tolerant (the MCP2515 board runs on 5V for its TJA1050: its SO line goes through a 1k/2k divider, the encoder is wired on its legs with the Pico's internal pull-ups, its board's + never on 5V). GPIO23/24/25/29 belong to the wireless chip, GP15 to the SDK's RP2040-E5 USB workaround.
- Pin constants in `src/firmware/board.h` and the tables in `docs/wiring.md` must stay in sync. Same for the panel size in `board.h` and `sim/main.c`.
